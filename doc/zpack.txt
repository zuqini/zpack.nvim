==============================================================================
1. INTRODUCTION                                           *zpack-introduction*

A thin layer on top of Neovim's native `vim.pack`, adding support for
lazy-loading and the widely adopted lazy.nvim-like declarative spec.
>lua
    -- ./lua/plugins/fundo.lua
    return {
      'kevinhwang91/nvim-fundo',
      dependencies = { "kevinhwang91/promise-async" },
      cond = not vim.g.vscode,
      version = 'main',
      build = function() require('fundo').install() end,
      opts = {},
      config = function(_, opts)
        vim.o.undofile = true
        require('fundo').setup(opts)
      end,
    }
<

4.1 DIRECTORY STRUCTURE                         *zpack-directory-structure*

    -- ./lua/plugins/fundo.lua

      version = 'main',
      build = function() require('fundo').install() end,
      opts = {},
      config = function(_, opts)
        vim.o.undofile = true
        require('fundo').setup(opts)
      end,
    }
<

4.2 COMMANDS                                                  *zpack-commands*

zpack provides a single user command, `:ZPack`, with subcommands. Rename it
with |zpack-setup-cmd_name|; a short name like `Z` or `Zp` saves typing.

                                                                      *:ZPack*
:ZPack {subcommand} [args]
                Runs one of the subcommands below. Subcommand names and plugin
                names tab-complete. Every subcommand except `reload` accepts a
                `!`.

:ZPack[!] update [plugin]
                Update every installed plugin except those with `pin = true`,
                or only the plugin named. A bulk update includes plugins that
                are installed but no longer in your spec. With `!`, apply the
                updates without the confirmation buffer. Tab completion lists
                registered plugin names. See |vim.pack.update()|. On Neovim
                0.13+ this is `:packupdate[!] [plugin]`.

                `pin` exists only in your specs. If a plugin's spec couldn't
                be read this session, a bulk update moves the plugin and
                rewrites its revision in the lockfile, and `:ZPack restore`
                can't undo that unless the lockfile is in git. Its `version`
                or `tag` still holds, because vim.pack takes an inactive
                plugin's version from the lockfile.

:ZPack[!] restore [plugin]
                Put every plugin, or the plugin named, back at the revision
                recorded in the lockfile, by calling |vim.pack.update()| with
                `target = 'lockfile'`. Use it to bring another machine in
                line, or to undo an update. With `!`, skip the confirmation
                buffer. A missing lockfile (`:ZPack update` creates one) or a
                failed restore is reported as an error. Tab completion lists
                registered plugin names. A bulk restore covers the same
                plugins as a bulk update. On Neovim 0.13+ this is
                `:packupdate[!] ++lockfile [plugin]`.

:ZPack[!] clean
                Delete installed plugins that your spec no longer lists. It
                lists them and asks first, defaulting to No, and
                `defaults.confirm = false` doesn't skip that prompt. With `!`
                it deletes without asking, which is meant for scripts. A
                headless run without `!` deletes nothing.

                A plugin whose spec couldn't be read this session, or that
                failed to add (a typo in its `url`, say), looks unused and is
                listed too. Read the list if startup reported an error.

:ZPack[!] build [plugin]
                Run the named plugin's build hook, without updating the
                plugin. `:ZPack! build` runs every plugin's hook. With neither
                a name nor `!` it only warns. Tab completion lists plugins
                that have a build hook.

:ZPack[!] load [plugin]
                Load the named plugin. `:ZPack! load` loads every plugin that
                hasn't loaded yet. With neither a name nor `!` it only warns.
                Tab completion lists unloaded plugins.

:ZPack[!] delete [plugin]
                Remove the named plugin from disk. `:ZPack! delete` removes
                every installed plugin. With neither a name nor `!` it only
                warns. Tab completion lists registered plugin names. Deleting
                a plugin that is in your spec can cause errors for the rest of
                the session; restart Neovim to install it again. On Neovim
                0.13+, `:ZPack delete {plugin}` is `:packdel! {plugin}` and
                `:ZPack! delete` is `:packdel! ++all`, except that the native
                command also removes installed plugins that aren't in your
                spec.

:ZPack[!] sync
                Update everything, then clean, as `:Lazy sync` does. The
                update is applied without the confirmation buffer; run
                `:ZPack update` on its own for a preview, and see there for
                `pin` in a spec that couldn't be read. Clean then asks as
                `:ZPack clean` does, or doesn't ask with `!`. Clean is skipped
                if the update raises an error, as when it is interrupted. One
                plugin's failed fetch doesn't stop it.

:ZPack reload {plugin}
                Re-source a plugin without restarting Neovim, as
                `:Lazy reload` does. It runs the plugin's `deactivate` hook
                (if it has one and the plugin has loaded), drops the plugin's
                modules from `package.loaded`, and loads it again from the
                start. A lazy plugin that hasn't loaded yet is loaded too,
                where `:Lazy reload` leaves it to its triggers. It reads the
                installed copy, so for a `dev = true` plugin run
                `:ZPack update {plugin}` first (see |zpack-Spec.dev|).

4.3 CONFIGURATIONS                                     *zpack-configurations*
                                                       *zpack-setup-defaults*
                                                          *zpack-performance*
>lua
    require('zpack').setup({
      -- { import = 'plugins' }  -- default import spec if not explicitly passed in via [1] or spec
      defaults = {
        confirm = true,          -- set to false to skip vim.pack install prompts (default: true)
        cond = nil,              -- global condition for all plugins, e.g. not vim.g.is_vscode (default: nil)
        lazy = false,            -- lazy-load every spec unless it sets lazy = false (default: false)
        version = nil,           -- version for specs that set no version/sem_version/branch/tag/commit (default: nil)
      },
      performance = {
        vim_loader = true,       -- enables vim.loader for faster startup (default: true)
      },
      cmd_name = 'ZPack',        -- :ZPack update, :ZPack clean, etc. (default: 'ZPack')
                                 -- use a shorter name like 'Z' or 'Zp' for fewer keystrokes
    })
<
Plugin-level settings always take precedence over `defaults`.

------------------------------------------------------------------------------
4.4 IMPORTING SPECS                                    *zpack-importing-specs*

>lua
    -- automatically import specs from `./lua/plugins/`, if there are any
    require('zpack').setup()

    -- or import from a custom directory e.g. `./lua/a/b/plugins/`
    -- or `setup({ spec = 'a.b.plugins' })`, or a list with the import in it
    require('zpack').setup('a.b.plugins')

    -- or point at a single spec file e.g. `./lua/plugins/telescope.lua`
    require('zpack').setup({ { import = 'plugins.telescope' } })

    -- or add your specs inline in setup
    require('zpack').setup({
      { 'neovim/nvim-lspconfig', config = function() ... end },
      ...
      { import = 'plugins.mini' }, -- or additionally import from `./lua/plugins/mini/`
    })

    -- or via the spec field
    require('zpack').setup({
      spec = {
        { 'neovim/nvim-lspconfig', config = function() ... end },
        ...
      },
    })
<

4.5 SETUP OPTIONS                                      *zpack-setup-options*

The `setup()` function accepts the following options:

                                                          *zpack-setup-spec*
spec            (table or string, optional)
                Array of plugin specs to load. Use this to define plugins
                inline instead of importing from a directory. A string is the
                module to import, and so is a string passed to `setup()`:
                `setup('custom.plugins')` is `{ import = 'custom.plugins' }`.

                Specs can also be passed directly in the setup table (without
                the `spec` key), as array elements or as one spec's fields,
                such as `{ import = 'custom.plugins', defaults = {...} }`.
                There `dev = true` is the spec's and a `dev` table is the
                option. Both forms work:
>lua
                -- Form 1: specs as array elements
                require('zpack').setup({
                  { 'nvim-lua/plenary.nvim' },
                  { 'nvim-telescope/telescope.nvim', cmd = 'Telescope' },
                })

                -- Form 2: explicit spec field
                require('zpack').setup({
                  spec = {
                    { 'nvim-lua/plenary.nvim' },
                    { 'nvim-telescope/telescope.nvim', cmd = 'Telescope' },
                  },
                })
<

                                                       *zpack-setup-cmd_name*
cmd_name        (string, optional)
                Name of the single user command. A short name such as `'Z'`
                or `'Zp'` saves typing. Must start with an uppercase letter
                and contain only letters and digits.
                Default: `'ZPack'`
                Examples:
                  - `'ZPack'` creates `:ZPack update`, `:ZPack clean`, etc.
                  - `'MyPack'`  creates `:MyPack update`, `:MyPack clean`, etc.
                  - `'Z'` creates `:Z update`, `:Z clean`, etc. (fewer keystrokes)

defaults        (table, optional)
                Default values that apply to all plugins. Plugin-level
                settings always take precedence over defaults.
                  - `confirm`: Ask before installing. Default: `true`
                  - `cond`: Global condition for all plugins.
                  - `lazy`: When `true`, every spec is lazy unless it sets
                    `lazy = false`, as with lazy.nvim's `defaults.lazy`.
                    Default: `false`.
                  - `version`: The version for specs that set none of
                    `version`/`sem_version`/`branch`/`tag`/`commit`, as with
                    lazy.nvim's `defaults.version`. A spec's `version = false`
                    opts out. Default: `nil`.

performance     (table, optional)
                Performance-related settings.
                  - `vim_loader`: Enable vim.loader caching. Default: `true`

                                                              *zpack-setup-dev*
dev             (table, optional)
                Where specs with `dev = true` come from, as with lazy.nvim's
                `dev` option. Such a spec's source becomes
                `path .. '/' .. name`. See |zpack-Spec.dev|.
                  - `path`: The directory holding your local checkouts.
                    Default: `'~/projects'`.
                  - `fallback`: When `true`, a spec whose checkout is missing
                    uses its regular `src` / `url` / `dir` / `[1]` source
                    instead. Default: `false`.

4.6 HEALTH CHECK                                              *zpack-health*

zpack ships a healthcheck. Run it to diagnose a broken or unexpected setup: >

    :checkhealth zpack
<
The report has these sections:

Environment     Confirms Neovim is 0.12.0+ and that `vim.pack` is available.

Setup           Whether |zpack.setup()| has been called. zpack is inactive
                until it has.

Configuration   Validates the resolved |zpack-setup-options|.

Plugins         A status summary of every registered plugin: how many are
                loaded, lazy, pending, installing, or disabled by `cond`.

Reporting a bug A minimal-config template and the steps for filing an issue.

5. WHY ZPACK?                                                *zpack-why-zpack*

Neovim 0.12+ includes a built-in package manager (`vim.pack`) that handles
plugin installation, updates, and version management. zpack is a thin layer
that adds lazy-loading capabilities and support for a lazy.nvim-like
declarative spec while completely leveraging the native infrastructure.

Features:
- completely native
    - Install and manage your plugins (including zpack) all within `vim.pack`
    - zpack shares the same native user experience as `vim.pack`
      — cloning, updates, lockfile, and version management. Your editor
      stays aligned with Neovim core's design philosophy and evolves
      with it
- batteries included
    - Add plugins using the same lazy.nvim spec provided by plugin authors
      you know and love
    - Minimal configurations necessary
- powers up `vim.pack` without the frills
    - Powerful lazy-loading triggers
    - Build triggers for installation/updates
    - Plugin management commands

zpack might be for you if:
- you want your plugin management to stay aligned with Neovim core's design
  philosophy, but you need a bit more out of the box
- you're a lazy.nvim user but don't use most of its advanced features. You
  just want a light plugin manager that works, backed by what's already
  built-in
- you want a manager that supports the lazy.nvim specs plugin authors
  already provide
- you simplified your config to use `vim.pack` as-is, but you miss
  lazy-loading, build hooks, plugin management commands, or drop-in
  lazy plugin specs

As a thin layer, zpack does not provide:
- A UI dashboard for your plugins (see |zpack-extensions|)
- Profiling, file watching, auto-reload or change detection.
  `:ZPack reload {plugin}` re-sources a plugin by hand. `dev = true` points a
  spec at a local checkout under `setup({ dev = { path } })`, which `vim.pack`
  clones like any other source, so an edit needs a commit and
  `:ZPack update {plugin}`.

If you're a lazy.nvim user, see |zpack-migrating-lazy|. If something you
need isn't achievable natively or through zpack, please submit an issue
or PR!

6.5 LAZY LOAD ON EVENT WITH PATTERN              *zpack-example-event-pattern*

Load plugin on specific events with file patterns:

Inline pattern:
>lua
    return {
      'rust-lang/rust.vim',
      event = 'BufReadPre *.rs',
    }
<

Or using EventSpec for multiple patterns:
>lua
    return {
      'user/polyglot-plugin',
      event = {
        event = 'BufReadPre',
        pattern = { '*.lua', '*.rs' },
      },
      opts = {},
    }
<

6.6 LAZY LOAD ON FILETYPE                                 *zpack-example-ft*

Load plugin when opening files of specific types. Automatically re-triggers

>lua
    return {
      'rust-lang/rust.vim',
      ft = { 'rust', 'toml' },
    }
<

6.7 CONDITIONAL LOADING                            *zpack-example-conditional*

Use `enabled` to skip `vim.pack.add` entirely, or `cond` to conditionally
load after calling `vim.pack.add`:
>lua
    return {
      'user/project-specific-plugin',
      enabled = vim.fn.has('linux') == 1, -- skip installation
      cond = function() return vim.fn.filereadable('.project-marker') == 1 end, -- skip loading
      opts = {},
    }
<

------------------------------------------------------------------------------
6.8 USING PLUGIN DATA IN HOOKS                     *zpack-example-plugin-data*

All lifecycle hooks (`init`, `config`, `build`, `cond`) and lazy-loading
triggers (`event`, `cmd`, `keys`, `ft`) can be functions that receive a
|zpack.Plugin| object containing the resolved plugin path and spec:
>lua
    return {
      'some/plugin',
      build = function(plugin)
        -- plugin.path: absolute path to the plugin directory
        -- plugin.spec: the vim.pack.Spec with resolved name, src, version
        vim.fn.system({ 'make', '-C', plugin.path })
      end,
    }
<

6.9 LOAD PRIORITY                                     *zpack-example-priority*

Control load order with priority (higher loads first; default: 50):
>lua
    -- to load colorscheme early
    return {
      'folke/tokyonight.nvim',
      priority = 1000,
      config = function() vim.cmd('colorscheme tokyonight') end,
    }
<

6.10 VERSION PINNING                                   *zpack-example-version*

`vim.pack.add` expects `string|vim.VersionRange`.

Pin a plugin to a semver range, branch, tag, or commit:
>lua
    return {
      'mrcjkb/rustaceanvim',
      version = vim.version.range('^6'), -- semver version
      -- version = 'main', -- branch
      -- version = 'v1.0.0', -- tag
      -- version = 'abc123', -- commit
    }
<
See |vim.pack.Spec|, |vim.version.range()|, and |vim.VersionRange|.

For lazy.nvim compatibility: ~
>lua
    return {
      'mrcjkb/rustaceanvim',
      sem_version = '^6',  -- corresponds to lazy.nvim spec's `version`
      -- branch = 'main',
      -- tag = 'v1.0.0',
      -- commit = 'abc123',
    }
<

zpack supports the `dependencies` field, allowing plugins to declare their

>lua
    return {
      'nvim-telescope/telescope.nvim',

7. SPEC REFERENCE                                       *zpack-spec-reference*
                                                                  *zpack-Spec*

>lua
    {
      -- Plugin source (provide at least one; src > url > dir > [1])
      [1] = "user/repo",                    -- GitHub short name, or a full git URL
      src = "https://...",                  -- Git URL, passed to git verbatim
      dir = "/path/to/plugin",              -- Local checkout (~ expanded; lazy.nvim compat)
      url = "https://...",                  -- Git URL (lazy.nvim compat)

      -- Dependencies
      dependencies = string|string[]|Spec|Spec[], -- Plugin dependencies

      -- Loading control
      enabled = true|false|function,        -- Enable/disable
      cond = true|false|function(plugin),   -- Condition to load
      lazy = true|false,                    -- Force eager (auto-detect)
      priority = 50,                        -- Load order (default: 50)
                                            --   doesn't order different ft patterns

      -- Plugin configuration
      opts = {},                            -- Options passed to setup()
      -- opts = function(plugin, opts) return {} end,
      opts_extend = { "ensure_installed" }, -- Concatenate these opts lists

      -- Lifecycle hooks
      init = function(plugin) end,          -- Runs before load
      config = function(plugin, opts) end,  -- Runs after load
      -- config = true,                      -- Calls require(main).setup({})
      build = string|function(plugin)       -- Build step:
            | (string|function(plugin))[]   --   ':<ex>' = ex-cmd; other = shell
            | false,                        --   array runs steps in order
                                            --   `false` opts out
      deactivate = function(plugin) end,    -- :ZPack reload teardown hook

      -- Lazy loading triggers (auto-sets lazy=true unless overridden)
      -- All triggers can also be functions receiving zpack.Plugin and the
      -- list so far, or `false`, which clears what earlier specs set

      -- Autocommand event(s). Supports 'VeryLazy' and inline patterns:
      -- "BufReadPre *.lua"
      event = string|string[]|EventSpec|(string|EventSpec)[]|fn(plugin),
      pattern = string|string[],            -- Global event pattern(s)
      cmd = string|string[]|fn(plugin),     -- Command(s) to create
      keys = string|string[]|KeySpec|KeySpec[]|fn(plugin, list)|false,
                                            -- Keymap(s) to create. A table of
                                            --   only strings is a list of keys,
                                            --   so { lhs, "dd" } is two keys:
                                            --   nest it or add a field
      ft = string|string[]|function(plugin), -- FileType(s) to lazy load on
                                            --   plugins sharing a filetype load
                                            --   together and re-trigger FileType
                                            --   once, after the last of them

      -- Source control (version for `vim.pack.add`, string|vim.VersionRange)
      version = "main",                     -- Branch/tag/commit
      -- version = vim.version.range("1.*"), -- Or semver range
      -- version = false,                    -- Opt out of defaults.version

      -- Source control (lazy.nvim compat, mapped to version)
      sem_version = "^1.0.0",               -- lazy.nvim's version field
      branch = "main",                      -- Git branch
      tag = "v1.0.0",                       -- Git tag
      commit = "abc123",                    -- Git commit

      -- Plugin metadata
      name = "my-plugin",                   -- Custom name (optional)
      main = "module.name",                 -- Explicit main module
      module = false,                       -- Disable module-based lazy loading

      -- Also from lazy.nvim
      pin = true,                           -- Exclude from :ZPack update bulk runs
      optional = true,                      -- Only install if also referenced
                                            --   non-optionally elsewhere
      dev = true,                           -- Clone the local checkout under
                                            --   setup({ dev = { path } })
      specs = { ... },                      -- Companion plugin specs grouped
                                            --   with this one (peers, not deps)

      -- Spec imports
      import = "plugins.lsp"                -- Module path string
            | function() return {...} end,  -- Or function returning specs
    }
<

                                                            *zpack-Spec.[1]*
[1]             (string, optional)
                `"owner/repo"`, or a full git URL. `owner/repo` expands to
                `https://github.com/owner/repo` unless `src`, `url` or `dir`
                is set. A full git URL (any `scheme://` URL, or scp-style
                `user@host:`) is used as it is, as in lazy.nvim. For a local
                path use |zpack-Spec.dir|.

                A name without an owner, such as "mason.nvim", refers to the
                plugin of that name that another spec defines, and never gives
                a source. With no such spec it is skipped with a warning, or
                without one if it is `optional`. lazy.nvim does the same.

                A spec needs at least one of [1], `src`, `dir` and `url`. When
                several are set, the source is the first of `src`, `url`,
                `dir`, [1]. The plugin's name still comes from [1], and specs
                with the same name merge into one plugin: see
                |zpack-Spec.name|.

                                                             *zpack-Spec.src*
src             (string, optional)
                Custom git URL for the plugin source. Passed to git
                verbatim: an absolute local path works, but `~` is not
                expanded. Use |zpack-Spec.dir| for local checkouts.
                Overrides [1] when both are set.

                                                             *zpack-Spec.dir*
dir             (string, optional)
                Local plugin directory. This is the field for local
                checkouts: the path is |expand()|ed, so `~` and environment
                variables work. lazy.nvim compatibility; mapped to `src`
                internally. Overrides [1] when both are set.

                                                             *zpack-Spec.url*
url             (string, optional)
                Custom git URL. For lazy.nvim compatibility.
                Mapped to `src` internally. Overrides [1] when both are
                set, e.g. to swap in a fork while keeping the short name.

                                                    *zpack-Spec.dependencies*
dependencies    (string|string[]|zpack.Spec|zpack.Spec[], optional)
                Plugins this one needs. They load before it when its lazy
                trigger fires. Give a string (a `[1]` value, see
                |zpack-Spec|), a spec, or a list of either. A dependency's
                spec can have its own `opts`, `config` and so on, and
                dependencies of its own.

                A plugin's specs merge in import order, and a spec under
                `dependencies` comes right after the spec that lists it, as in
                lazy.nvim. So the later spec wins, whether it sits under
                `dependencies` or at the top level.

                Disabled and `optional` plugins follow lazy.nvim:
                - A dependency whose specs are all `optional` is skipped like
                  any other plugin.
                - A disabled dependency doesn't disable the plugin listing it.
                - When the parent is disabled or skipped as `optional`, the
                  specs under its `dependencies` and `specs` are dropped with
                  it. They no longer configure or add dependencies to a plugin
                  that other specs keep, and an `enabled = false` under a
                  disabled parent no longer disables it. That plugin keeps its
                  name even if a dropped spec set `name`, and keeps its source
                  while a remaining spec gives it; otherwise its remaining
                  specs pick one.
                - `enabled = false` under an `optional` parent still applies,
                  since optional plugins are skipped only once nothing else is
                  disabled.

                A plugin skipped by `cond` keeps its dependency specs.

                A spec table listed under several plugins stays while any of
                them does, and counts once. It is a dependency only if every
                remaining listing is under `dependencies`; lazy.nvim records
                only its first listing.

                                                         *zpack-Spec.enabled*
enabled         (boolean|function, optional)
                Whether the plugin is used at all: a disabled plugin isn't
                installed. Can be a function returning a boolean. When several
                specs set it, the last one wins, as in lazy.nvim:
                `enabled = true` undoes an earlier `enabled = false`, and only
                that spec's function runs. A spec under `dependencies` counts
                too (see |zpack-Spec.dependencies|).

                                                            *zpack-Spec.cond*
cond            (boolean|function(plugin), optional)
                Whether to load the plugin. A plugin with a false `cond` is
                still installed. Can be a function that receives
                |zpack.Plugin| and returns a boolean. When several specs set
                it, the last one wins, as for |zpack-Spec.enabled|. On a spec
                with an `import`, the function gets no plugin argument for the
                import: see |zpack-Spec.import|.

                                                            *zpack-Spec.lazy*
lazy            (boolean, optional)
                `false` loads the plugin at startup even if it has
                lazy-loading triggers. When unset, a plugin is lazy if it has
                a trigger.

                `:colorscheme x` first loads the plugin holding `colors/x.vim`
                or `colors/x.lua` if it hasn't loaded yet, as in lazy.nvim.
                So:
                - A lazy colorscheme plugin loads when its scheme is set.
                - A colors file can use its plugin's `autoload/` and modules,
                  also from an `init`.
                - An eager plugin whose scheme is set from an earlier plugin's
                  `config` (one with a higher `priority`, or the same
                  `priority` and listed first) loads there, before its turn.
                  themery.nvim does this when it restores the saved scheme.
                - With `setup()` at |VimEnter| or from a `plugin/` script, its
                  scripts have run by then, so it gets only its colors file
                  until its turn. Give it the higher `priority`.

                                                        *zpack-Spec.priority*
priority        (number, optional)
                Higher values load earlier. Default: 50. It orders eager
                plugins at startup, and lazy plugins waiting on the same
                trigger, such as the same event. It doesn't order different
                `ft` patterns, such as a literal and a glob: each loads when
                its own pattern's turn comes. Raise it for a colorscheme, or
                for a plugin that others depend on.

                                                            *zpack-Spec.opts*
opts            (table|function(plugin, opts), optional)
                Options for the plugin's `setup()`. With `opts` and no
                `config` function, zpack calls `require(main).setup(opts)`.
                With a `config` function, the resolved opts are its second
                argument and calling `setup()` is up to you.

                A function receives |zpack.Plugin| and the opts merged so far
                from the plugin's earlier specs, and returns a table or edits
                the one it was given. If it throws, the error is reported and
                the plugin loads without `config` or `setup()`, as in
                lazy.nvim.

                Set a key to `vim.NIL` to remove it, as in lazy.nvim. That
                works only where specs merge:
                - at the top level of opts, unless these opts or the earlier
                  ones are a non-empty list;
                - in a table merged into one that an earlier spec set at the
                  same place.

                A table that replaces the earlier value keeps a `vim.NIL`
                inside it. That is the case when nothing, a scalar or a
                non-empty list was there, or when the table is a non-empty
                list itself. Opts that a function returns or edits keep it
                too. To hand a plugin a JSON `null` (in LSP settings, for
                example), nest it in a table no earlier spec sets, or set it
                from a function.

                Each opts function, `config` and `setup()` gets its own copy
                of the plain tables in opts, so editing opts in place never
                reaches your specs. A table with a metatable (other than
                |vim.empty_dict()|'s) is not copied.

                                                     *zpack-Spec.opts_extend*
opts_extend     (string|string[], optional)
                Keys in `opts` whose lists are appended across the plugin's
                specs instead of replaced. Use dots for a nested key, such as
                `"sources.default"`.
>lua
                -- plugins/treesitter.lua
                { 'nvim-treesitter/nvim-treesitter',
                  opts_extend = { 'ensure_installed' },
                  opts = { ensure_installed = { 'bash', 'c' } } }
                -- plugins/rust.lua
                { 'nvim-treesitter/nvim-treesitter',
                  opts = { ensure_installed = { 'rust' } } }
                -- ensure_installed ends up with bash, c and rust
<
                Set it on any one of the plugin's specs: zpack combines
                `opts_extend` from all of them, and no spec can turn it off.
                To replace an extended list, use function-form opts, e.g.
                `function(_, o) o.ensure_installed = { 'x' } end`.

                - Lists append in merge order, which is import order (see
                  |zpack-Spec.dependencies|).
                - Duplicates are kept. nil holes in a list are dropped when
                  specs merge.
                - A table with named keys at that path, such as which-key's
                  `{ mode = 'v', { ... } }`, is appended as one entry, so its
                  keys apply only to its own entries. Two dicts at that path
                  deep-merge as usual.
                - Specs under the `dependencies` or `specs` of a plugin that
                  is disabled or skipped as `optional` are left out, as in
                  lazy.nvim.

                lazy.nvim differs in two ways:
                - Each spec uses the nearest `opts_extend` at or before it. A
                  spec with none in effect replaces the lists before it, so of
                  the lists set before the first `opts_extend`, only the last
                  is kept, and a later `opts_extend` that leaves a key out
                  stops that key from appending.
                - It keeps only the list entries of a table at that path, so
                  named keys are dropped and a dict there becomes an empty
                  list.

                                                            *zpack-Spec.init*
init            (function(plugin), optional)
                Runs before the plugin loads, unless an earlier `init` already
                loaded it. Receives |zpack.Plugin|. Inits run during
                `setup()`, highest `priority` first, before the eager plugins
                load.

                A `require` of an eager plugin's module from an `init` loads
                that plugin there, as in lazy.nvim: its dependencies first,
                then its `config`. When `setup()` runs from `init.lua`, its
                `plugin/` scripts still run in their usual place, after every
                `init`, where lazy.nvim sources them during the `init`. A lazy
                dependency it loads sources after the eager plugins.

                A lazy plugin's `cmd`, `event`, `ft` and `keys` are set up
                before the inits, as in lazy.nvim, so an `init` that uses one
                of them loads that plugin.

                A function-form trigger is called before the inits too. It
                doesn't see what the inits set, and a `require` in it loads
                the plugin holding the module right there, before every
                `init`, its own included. lazy.nvim loads that plugin after
                the inits. Require inside the key's or command's function
                instead. An `event` or `ft` function has no such place: return
                a static list, and use the module in the plugin's `config` or
                an autocmd's callback.

                                                          *zpack-Spec.config*
config          (function(plugin, opts)|true, optional)
                Runs after the plugin loads. A function receives
                |zpack.Plugin| and the resolved `opts`, and replaces the
                automatic `setup()` call. `true` makes zpack call
                `require(main).setup(opts)` even when no spec sets `opts`.

                                                           *zpack-Spec.build*
build           (string|function(plugin)|(string|function(plugin))[]|false,
                optional)
                What to run after the plugin is installed or updated: a
                string, a function, or a list of them, run in order. A string
                starting with `:` is an Ex command; any other string runs with
                `sh -c` (`cmd.exe /c` on Windows) in the plugin's directory. A
                function receives |zpack.Plugin|. `false` opts out.

                                                           *zpack-Spec.event*
event           (string|string[]|EventSpec|(string|EventSpec)[]|fn(plugin, list)|false,
                optional)
                Autocommand event(s) that load the plugin. Setting it makes
                the plugin lazy. Give an event name, a |zpack.EventSpec| for
                an event with patterns, or a list mixing the two. A pattern
                can also go inline: "BufReadPre *.lua". 'VeryLazy' is
                supported.

                A function receives |zpack.Plugin| and the list so far, and
                returns any of those forms or edits the list. `false` clears
                the events that earlier specs set, in import order (see
                |zpack-Spec.dependencies|). Both also hold for `cmd`, `keys`
                and `ft`. A function in any of the four is called before the
                inits: see |zpack-Spec.init| for what a `require` in it does.

                zpack fires `User VeryLazy` once on UIEnter, or right after
                `setup()` if Neovim has already started, so your own config
                can hook |autocmd| `User VeryLazy` for work that should wait
                until then.

                                                         *zpack-Spec.pattern*
pattern         (string|string[], optional)
                Pattern(s) for every event in `event` that has none of its
                own. Plain event names use it; an EventSpec's own `pattern`
                takes precedence. Default: '*'.

                                                             *zpack-Spec.cmd*
cmd             (string|string[]|function(plugin, list)|false, optional)
                Command(s) that load the plugin. Setting it makes the plugin
                lazy. zpack creates each command, and tab completion on it
                loads the plugin too, so the real command's completer answers
                on the first press.

                A function receives |zpack.Plugin| and the list so far, and
                returns the value or edits the list. It is called before the
                inits: see |zpack-Spec.init| for what a `require` in it does.
                `false` clears the commands that earlier specs set.

                                                            *zpack-Spec.keys*
keys            (string|string[]|zpack.KeySpec|zpack.KeySpec[]|function(plugin, keys)|false,
                optional)
                Keymap(s) that load the plugin. Setting it makes the plugin
                lazy. See |zpack.KeySpec| for the fields of one key.

                A table of only strings is a list of keys, so
                `{ "<leader>d", "dd" }` is two keys. To make it one key with
                an rhs, nest it or add a field. The exception is a second
                string that can only be an rhs: empty, `<Nop>`, starting with
                `<cmd>`, `<Plug>` or `:`, or with text before a final `<CR>`.

                A function receives |zpack.Plugin| and the keys so far (as
                KeySpec tables with duplicates removed), and returns the value
                or edits the list. It is called before the inits: see
                |zpack-Spec.init| for what a `require` in it does. `false`
                clears the keys that earlier specs set.

                Across specs, as in lazy.nvim, a later key replaces an earlier
                one with the same lhs, mode, ft and buffer, and a `false` or
                |vim.NIL| rhs disables it. The plugin stays lazy if every key
                is disabled. Specs merge in import order, including those
                under `dependencies` (see |zpack-Spec.dependencies|).

                As in lazy.nvim, when a plugin starts to load, however it
                loads, it drops the proxies of its keys that no other pending
                plugin lists, so its `plugin/` and `config` find them free. A
                key that a pending plugin lists keeps its proxy until that
                plugin loads, so another plugin's key on the same lhs, mode,
                ft and buffer, eager or lazy, isn't mapped over it.

                                                              *zpack-Spec.ft*
ft              (string|string[]|function(plugin, ft)|false, optional)
                Filetype(s) that load the plugin. Setting it makes the plugin
                lazy. After loading, zpack re-triggers BufReadPre, BufReadPost
                and FileType so that LSP clients and Treesitter attach.

                A function receives |zpack.Plugin| and the list so far, and
                returns the value or edits the list. It is called before the
                inits (see |zpack-Spec.init|). `false` clears the filetypes
                that earlier specs set. A value with no filetypes warns and
                the plugin never loads from it; an invalid pattern warns and
                is skipped.

                Plugins sharing a filetype load together in priority order and
                re-trigger once, after the last of them:
                - A plugin's `config` doesn't see `ftplugin` or BufRead
                  handler effects from others in the group, even with
                  `dependencies` declared. Read such values from a FileType
                  handler or the plugin's own `ftplugin` instead.
                - If several plugins ship an `ftplugin` guarded by
                  `b:did_ftplugin` that don't set `b:undo_ftplugin`, the
                  lowest-priority plugin wins.
                - If a plugin's `config` loads another buffer of that
                  filetype, FileType handlers of plugins still pending in the
                  group miss that buffer. Declaring the pending plugin as a
                  dependency avoids this.
                - A plugin with `event = 'FileType'` between them in priority
                  order splits the group, whatever its pattern, and each part
                  re-triggers.

                                                         *zpack-Spec.version*
version         (string|vim.VersionRange, optional)
                A git branch, tag or commit as a string, or a semver range
                from |vim.version.range()|. This is vim.pack.add's `version`
                field.

                A string that can't be a git ref, because it contains `*` or
                starts with `^`, `~`, `<`, `>` or `=`, is read as a semver
                range, as in lazy.nvim. For a range like `1.x`, which could
                also be a branch, use `sem_version`.

                If no tag fits a range written as a string (here, in
                `sem_version` or in `defaults.version`), the plugin follows
                its default branch, as in lazy.nvim. A |vim.version.range()|
                object keeps vim.pack's behaviour, which is an error if no tag
                fits.

                A plugin's version is fixed for the session. If upstream later
                adds a tag that fits, or the spec moves to a range that only a
                fetch finds a tag for, `:ZPack update` and `:ZPack sync` still
                move the plugin to the branch's tip, and say so. Restart and
                update again to move it to the tag.

                `false` opts out of `defaults.version` and `sem_version`.

                When a plugin's specs set several version fields, the order is
                lazy.nvim's: `commit`, `tag`, `version`, `sem_version`,
                `branch`, then `defaults.version`, which applies only when
                none of the others is set.

                                                     *zpack-Spec.sem_version*
sem_version     (string, optional)
                Semver range string. Corresponds to lazy.nvim spec's
                `version` field. Auto-wrapped to |vim.version.range()|.
                For lazy.nvim compatibility.

                                                          *zpack-Spec.branch*
branch          (string, optional)
                Git branch. For lazy.nvim compatibility.
                Mapped to `version` internally.

                                                             *zpack-Spec.tag*
tag             (string, optional)
                Git tag. For lazy.nvim compatibility.
                Mapped to `version` internally.

                                                          *zpack-Spec.commit*
commit          (string, optional)
                Git commit hash. For lazy.nvim compatibility.
                Mapped to `version` internally.

                                                            *zpack-Spec.name*
name            (string, optional)
                The plugin's name, in place of the one derived from [1] (or
                from the source URL when there is no [1]). Set it when you
                need a particular directory name, or to keep apart two plugins
                that would get the same name.

                Specs with the same name are folded into one plugin, as in
                lazy.nvim. When their sources differ, as with `old-owner/repo`
                and `new-owner/repo`, the source comes from, in order:
                1. a spec with `dev = true`;
                2. a spec with an explicit `src`, `url` or `dir`;
                3. a top-level spec rather than a dependency.

                Among equals, the last one imported wins. zpack warns unless
                the specs name a repo in common: a shared [1], or a
                `src`/`url` equal to the other's [1].

                That picks only the source. Fields merge in import order as
                usual, so `enabled = false` on one spec disables the plugin
                unless a later spec sets `enabled`.

                                                            *zpack-Spec.main*
main            (string, optional)
                The module zpack calls `setup()` on. When unset, zpack works
                it out:
                1. For mini.* plugins, the plugin name.
                2. A module matching the plugin name without its `vim-` or
                   `nvim-` prefix and its `.vim` or `.nvim` suffix.
                3. Otherwise, as in lazy.nvim, the one module in the plugin's
                   `lua/`, if there is only one (`null-ls` for none-ls.nvim).

                Set it when detection fails.

                                                          *zpack-Spec.module*
module          (boolean, optional)
                `false` stops a `require` of the plugin's modules from loading
                it. Default: `true`.

                By default, a `require` loads the pending lazy plugin that
                holds the module's file under `lua/` (`.lua`, `/init.lua`, or
                a compiled `.so` or `.dll`). Of several such plugins, the one
                named like the top-level module loads, as in lazy.nvim, so
                `require('mini.ai')` loads `mini.nvim` rather than a
                standalone `mini.ai`. Otherwise the first listed loads, higher
                `priority` first. A plugin that has only the module's
                top-level name, such as `mini.pairs` for a `require` of
                `mini.icons`, stays lazy, and the `require` fails as usual.

                                                          *zpack-Spec.import*
import          (string|function, optional)
                A module to read specs from, such as 'plugins' or
                'plugins.lsp'. Each file should return a spec or a list of
                specs. zpack warns if it finds no specs.

                If lua/{path}.lua exists, it is the only file read, just as
                foo.lua shadows foo/init.lua for Lua's `require`. Otherwise
                zpack reads every .lua file in lua/{path}/ and every
                lua/{path}/*/init.lua, in order of module name as lazy.nvim
                does. lua/{path}/init.lua is the module {path}.

                `import` can also be a function, as in lazy.nvim. It is called
                inside pcall, and a table it returns is read as a spec list.

                A string `import` is looked up under your config's `lua/`
                directory, then on 'runtimepath', then in the plugins that
                `import` specs add this run, including later ones. What
                happens when none of those has the module depends on where the
                `import` is:

                - On a plugin's spec, such as
                  `{ "user/dist", import = "dist.plugins" }`, zpack looks in
                  that plugin, installing it if needed. A plugin that's
                  disabled or removed isn't installed.
                - On its own, as in
                  `{ { "user/dist" }, { import = "dist.plugins" } }`, zpack
                  looks in the plugins your specs list and don't disable whose
                  name or repository is named after the module's top level, as
                  `dist` is for `dist.plugins`. It installs those that are
                  missing, on the first start as on later ones.

                Either way the plugin installs from what your config's specs
                say about it. A `version` or `url` set only inside its own
                modules applies from the next session and the next
                `:ZPack update`, as in lazy.nvim.

                For an `import` on its own, lazy.nvim tries the plugins named
                after the module first and then every other plugin. zpack
                looks no further, so for a module named otherwise put the
                `import` on its plugin's spec. Unlike lazy.nvim, zpack finds a
                plugin listed after the `import`, and doesn't read one that's
                disabled or removed. The search reads your specs a second time
                at every start, so the `import` on its plugin's spec is also
                the faster form.

                `enabled` and `cond` on the spec decide whether to follow the
                `import`, as in lazy.nvim. Here `cond` works like `enabled`:
                if it is false, the module isn't read and its plugins aren't
                registered, so they aren't installed and `:ZPack clean` treats
                installed ones as unused. To keep them installed but unloaded,
                set `cond` on the plugins themselves, or use `defaults.cond`,
                which doesn't apply to the `import` itself. A function-form
                `cond` gets no plugin here, as in lazy.nvim. On a spec with
                both a source and an `import`, the plugin keeps the usual
                meaning of each field, and its `cond` also runs for the
                `import`.

                                                            *zpack-Spec.pin*
pin             (boolean, optional)
                `true` keeps the plugin out of a bulk `:ZPack update`, as in
                lazy.nvim. It is still installed, and naming it, as in
                `:ZPack update {name}`, still updates it.

                                                       *zpack-Spec.optional*
optional        (boolean, optional)
                `true` includes the plugin only if another spec refers to it
                without `optional`, in its `dependencies` list for example. A
                plugin whose specs are all optional is dropped without a
                message. As in lazy.nvim.

                                                            *zpack-Spec.dev*
dev             (boolean, optional)
                `true` takes the plugin from your local checkout: its source
                becomes |zpack-setup-dev|'s `path` plus the plugin's name. A
                plugin's author can work on it this way without changing the
                spec they publish. Unlike lazy.nvim, which uses the checkout
                in place, |vim.pack| clones it as it does any other source. An
                edit reaches Neovim once it is committed, on the branch the
                checkout had when it was installed, and
                `:ZPack update {plugin}` has run.

                                                          *zpack-Spec.specs*
specs           (zpack.Spec|zpack.Spec[], optional)
                More plugin specs to declare along with this one, as in
                lazy.nvim. Unlike `dependencies`, they aren't loaded before
                this plugin: each becomes a plugin of its own. They are
                dropped with this plugin when it is disabled or skipped as
                `optional` (see |zpack-Spec.dependencies|).

                                                     *zpack-Spec.deactivate*
deactivate      (function(plugin), optional)
                Called by `:ZPack reload {plugin}` before the plugin is
                sourced again, as in lazy.nvim. A plugin that hasn't loaded
                yet has nothing to tear down, so the hook is skipped for it.
                Use it to remove the autocommands, keymaps or watchers the
                plugin set up when it loaded. If it throws, the error is shown
                as a warning and the reload goes on.

10. KEYSPEC REFERENCE                              *zpack-keyspec-reference*
                                                             *zpack.KeySpec*

>lua
    {
      [1] = "<leader>ff",             -- LHS keymap (required)
      [2] = function() end|"rhs",     -- RHS (optional), see below
      desc = "description",           -- Keymap description
      mode = "n"|{"n","v"},           -- Mode(s), default: "n"
      ft = "lua"|{"lua","vim"},       -- FileType scope; install buffer-locally on matching FileType only
      buffer = true|0|7,              -- Buffer scope: true/0 = current buffer; integer = specific buffer
      remap = true|false,             -- Allow remapping, default: false
      nowait = true|false,            -- Default: false
      expr = true|false,              -- RHS is an expression, default: false
      silent = true|false,            -- Suppress command-line output, default: false
      noremap = true|false,           -- Inverse of `remap` (lazy.nvim alias)
      replace_keycodes = true|false,  -- Replace keycodes in expr result; defaults to true when expr is true
    }
<

                                                        *zpack.KeySpec.[1]*
[1]             (string, required)
                The left-hand side of the keymap (e.g., `<leader>ff`).

                                                        *zpack.KeySpec.[2]*
[2]             (string|function|false, optional)
                The right-hand side: a function, or a string as for
                |vim.keymap.set()|. Omit it for a key that only loads the
                plugin: the press then goes to what the plugin or Neovim
                maps it to. `false` or |vim.NIL| disables an earlier spec's
                key, see |zpack-Spec.keys|.

                                                        *zpack.KeySpec.desc*
desc            (string, optional)
                Description of the keymap.

                                                        *zpack.KeySpec.mode*
mode            (string|string[], optional)
                Mode(s) for the keymap. Default: "n" (normal mode).

                                                       *zpack.KeySpec.remap*
remap           (boolean, optional)
                Whether to allow remapping (recursive mapping). When false,
                the mapping is non-recursive (like noremap). Default: false.
                Wins over the `noremap` alias when both are set.

                                                      *zpack.KeySpec.nowait*
nowait          (boolean, optional)
                Whether to use nowait. Default: false.

                                                        *zpack.KeySpec.expr*
expr            (boolean, optional)
                Whether the right-hand side is an expression. When true, the
                returned value of the rhs is used as the keys to feed.
                Default: false.

                                                      *zpack.KeySpec.silent*
silent          (boolean, optional)
                Whether the keymap should be silent (suppress command-line
                output). Default: false.

                                                     *zpack.KeySpec.noremap*
noremap         (boolean, optional)
                The inverse of `remap`, accepted because lazy.nvim accepts
                it. Used only when `remap` is unset. When neither is set, the
                keymap is not remapped, as with `remap = false`.

                                            *zpack.KeySpec.replace_keycodes*
replace_keycodes (boolean, optional)
                When `expr` is true, replace keycodes in the resulting
                string. Default: true when `expr` is true; otherwise unused.

                                                      *zpack.KeySpec.buffer*
buffer          (integer|boolean, optional)
                Buffer scope, as in lazy.nvim. `true` or `0` maps the key in
                the current buffer only, and an integer in that buffer. It
                applies to both the lazy proxy and the real keymap.

                                                          *zpack.KeySpec.ft*
ft              (string|string[], optional)
                Filetype scope, as in lazy.nvim. Both the lazy proxy and the
                real keymap are mapped only in buffers of the given
                filetype, including buffers opened later.

                                                       *zpack.KeySpec.nop*
A KeySpec whose `[2]` is `'<Nop>'` (any case) or the empty string is mapped as
a real no-op, not as a lazy proxy, so pressing the key never loads the plugin.
Use it to suppress a default mapping the plugin would otherwise install.
lazy.nvim does the same (`Util.is_nop`).

11. TIPS & MIGRATION                                *zpack-tips-and-migration*

------------------------------------------------------------------------------
11.1 MIGRATING FROM LAZY.NVIM                          *zpack-migrating-lazy*

Most of your lazy.nvim plugin specs will work as-is with zpack. However,
zpack follows `vim.pack` conventions over lazy.nvim conventions, and is
missing a few advanced features:

                                                       *zpack-migration-spec*
version pinning           lazy.nvim's `version` field maps to zpack's
                          `sem_version`. See |zpack-example-version|.

                                                        *zpack-migration-dev*
dev mode                  Set `dev = true` on a spec and
                          `setup({ dev = { path = '~/projects' } })`, and
                          the source becomes `<path>/<plugin-name>`. See
                          |zpack-Spec.dev| and |zpack-setup-dev|. The
                          checkout is cloned, not used in place: commit an
                          edit and run `:ZPack update {plugin}` to pick it
                          up. There is no file watching or auto-reload;
                          `:ZPack reload {plugin}` re-sources a plugin by
                          hand.

                                                  *zpack-migration-profiling*
profiling                 Use `nvim --startuptime startuptime.log`.
                          Also see: https://gist.github.com/zuqini/35993710f81983fbfa6baca67bdb32ed

                                               *zpack-migration-default-lazy*
default lazy plugins      lazy.nvim's community specs silently default
                          top-level specs for utility libraries like
                          `plenary.nvim` to `lazy = true`, even without
                          lazy triggers or a lazy parent. zpack respects
                          your specs as-written, so set `lazy = true`
                          explicitly on such specs if you want the same
                          default, or set `defaults.lazy = true` in
                          `setup()` to apply it to every spec.

                                              *zpack-migration-enabled-cond*
enabled vs cond           lazy.nvim collapses both to a single "disabled"
                          state. zpack splits them: `enabled = false` skips
                          install entirely (the plugin is never cloned),
                          while `cond = false` installs the plugin but
                          skips its load (so it still shows up under
                          `vim.pack`'s data dir). Use `enabled` when you
                          want lazy.nvim's "don't install at all" behavior.
                          On a spec with an `import`, a false `cond` works
                          like `enabled` for what the import declares: see
                          |zpack-Spec.import|.

                                                 *zpack-migration-shadowed*
shadowed runtime files    When `setup()` runs from `init.lua` and two eager
                          plugins ship the same runtime file, such as
                          `colors/x.lua`, the higher `priority` plugin wins,
                          being first on 'runtimepath'. In lazy.nvim the lower
                          `priority` one wins, since it loads later and goes
                          ahead of the other.

11.2 GOTCHAS                                                   *zpack-gotchas*

Known gotchas when using zpack:

                                                *zpack-gotcha-install-update*
install/update feedback   `vim.pack` reports install and update progress
                          through `:messages` (e.g. "vim.pack: Downloading
                          updates (0/83)"). You won't see them with
                          `vim.opt.cmdheight = 0`. Raise it, check
                          `:messages`, or route them through a notifier:
                          - https://github.com/folke/snacks.nvim
                          - https://github.com/rcarriga/nvim-notify
                          - https://github.com/folke/noice.nvim
                          Also see |zpack-tip-noice| for compatibility
                          notes.

11.3 COMPATIBILITY NOTES                              *zpack-compat-notes*

Workarounds for third-party plugins that assume lazy.nvim or filter out
`vim.pack` messages.

                                                         *zpack-tip-snacks*
SNACKS.NVIM DASHBOARD ~

The default Snacks.nvim dashboard configuration includes a startup time
section that has a hard dependency on lazy.nvim. This will cause errors with
any plugin manager other than lazy.nvim, not just zpack.

To work around this, remove the startup section from your dashboard config:
>lua
    require('snacks').setup({
      dashboard = {
        sections = {
          { section = "header" },
          { section = "keys", gap = 1, padding = 1 },
          -- { section = "startup" }, -- Remove (depends on lazy.nvim)
        },
      }
    })
<
See: https://github.com/folke/snacks.nvim/issues/1778

                                                          *zpack-tip-noice*
NOICE.NVIM WITH VIM.PACK ~

noice.nvim filters out `vim.pack` messages by default, which means you
won't see install/update notifications from your plugin manager.

To fix this, add a route that explicitly shows `vim.pack` messages:
>lua
    require('noice').setup({
      routes = {
        {
          filter = {
            event = "msg_show",
            find = "vim.pack",
          },
        },
      },
    })
<

11.4 LOCKFILE LOCATION                                        *zpack-lockfile*

`vim.pack` writes its lockfile to `$XDG_CONFIG_HOME/nvim/nvim-pack-lock.json`,
next to your `init.lua`. On Neovim 0.13+ the path is configurable through the
|'packlockfile'| option, so you can keep it out of your config repo:
>lua
    vim.o.packlockfile =
      vim.fs.joinpath(vim.fn.stdpath('data'), 'nvim-pack-lock.json')
<
Two caveats:
- 'packlockfile' must be set before the first |vim.pack| call, which in
  practice means before the `vim.pack.add()` that installs zpack itself.
  Put it at the very top of your `init.lua`.
- Changing the path does not move the existing file. Move (or delete and
  regenerate with `:ZPack update`) the old lockfile, otherwise `vim.pack`
  starts from an empty one.

zpack needs no configuration for this: `:ZPack update`, `:ZPack restore` and
installing a plugin at its locked revision all follow whatever 'packlockfile'
points at.

------------------------------------------------------------------------------
11.5 NATIVE VIM.PACK COMMANDS                          *zpack-native-commands*

On Neovim 0.13+, several `:ZPack` subcommands map to native `vim.pack`
commands (`:packupdate`, `:packdel`); zpack keeps its session state in sync
either way. The native commands don't know about specs, so they ignore `pin`:
`:packupdate!` moves a `pin = true` plugin that `:ZPack! update` leaves alone.
See |zpack-commands| for the full mapping. Reach for the native commands when
you want their extra flags, for example `:packupdate ++offline`.
